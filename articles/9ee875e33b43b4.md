## 先にまとめ

これから書いていく通りに情報の洪水に対して、イベント駆動と[川島さんのイミュータブルデータモデル](https://scrapbox.io/kawasima/%E3%82%A4%E3%83%9F%E3%83%A5%E3%83%BC%E3%82%BF%E3%83%96%E3%83%AB%E3%83%87%E3%83%BC%E3%82%BF%E3%83%A2%E3%83%87%E3%83%AB)の考えを自分なりに咀嚼して、作っているAltへの適用を試みた。その過程を記す。
RSSフィードを多数購読すると問題が出てくる。それは、情報の洪水だ。

フィードが次々流れて読み切れない。翌日、いや下手したら数時間後、数分後には、何を読んだか忘れている。

これはSNSなどの受動的なアプリケーションと同様の問題だと思う。ただ時間が消費される。
そこで知識として活用できる形へと、情報を加工して血肉となるものへ変える必要が出てきた。
Claude Codeを活用しつつ、イベントソーシングやイミュータブルデータモデルの考えを採り入れたので、その経験を共有したい。

まずは、ざっと要旨をまとめる
- 散らばっていた各機能が統合され、情報を価値のある知識へと昇華させられた
- マイクロサービスが20以上あるシステムだと、Claude CodeのOpus 4.6でも実装を誤る
- 加えて、イベントソーシングやイミュータブルデータモデルなどの高度で抽象的な考えを取り入れるには、専用のClaude CodeのSKILLが必須だった
- このアーキテクチャ（append-only）には、データが急速に増大するという課題が構造的上存在する
- デメリットとしては、機能が統合された分、システムは複雑になった

## イミュータブルデータモデル導入の動機

ブログを今まで4本書いてきた。
機能を追加しようか考えていた時にLLMと壁打ちしていて、既存のマイクロサービスからなる機能がバラバラの方向を向いて、機能として散らばっていることに気が付いた。

機能はある、しかしアプリケーションとしてのまとまりがない。
そんなことに気づいた。

具体的に当時あった機能を列挙していくと

| カテゴリ | 機能 |
| --- | --- |
| 収集 | RSSフィードの登録・収集 |
| 閲覧 | RSSフィードの閲覧（未読/既読の一覧表示） |
| 取得 | ユーザー操作による記事の取得 |
| 整理 | 記事のタグ付け |
| 整理 | 記事の索引生成 |
| 検索 | フィードと記事を横断した全文検索 |
| 要約・翻訳 | 記事のリアルタイム要約＆翻訳 |
| 振り返り | 過去3日間の既読記事の振り返り |
| 質問応答 | RAGベースの質問応答 |
| 可視化 | 簡易的なダッシュボード機能 |
| 可視化 | タグの3次元可視化 |

ざっとこれくらいだったと思う。
機能は十分ある。でもUIが分断されているし、それぞれの機能に繋がりがない。
これらを分類すると、「収集」「閲覧」「検索」「質問」「振り返り」「可視化」にだいたい分けられると思う。
そしてAltもそうだし、既存の「読む」ことに特化したサービスや、既存のメディア消費が抱える構造的な問題があると気づいた。
情報を消費するが、受け身で終わってしまう。
そして問題なのは、思い出せない情報は探せないということだ。
意識に無いものは探さない。


これらをイベント駆動とイミュータブルデータモデル
でユーザーアクション種別を記録し、思い出させる。
それができたら、ただ情報を消費するに留まらないと思った。

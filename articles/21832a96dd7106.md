# 宣言的に管理できるフォーマットを作った

これです。

https://github.com/Kaikei-e/LKAL

LKAL（Literals, Keys, and Labels）は、あるべき状態を宣言するための小さなデータ形式です。値の型は書き方だけで決まり、構造は{}だけで表し、すべての項目を名前付きのパスで一意に指せます。Goのリファレンス実装と、検査・整形・JSON変換・パス編集を行うlkalコマンドを公開しています。

## 既存フォーマットの扱いづらい点

アプリケーション開発をしていて、JSONやYAMLで管理されているものは本当に多くあります。
しかし、これらのフォーマットでは下記の点が個人的には使いにくく感じました。

JSONは...
- コメントが書けない
  - 方言ごとに仕様の有無も中身も異なり、互換性がない
- 「null」と「キーを書かない」の2通りで不在を示すため、前者2つと「存在する」の3通りで表現される
- オブジェクト内のキー名は一意である"べき"（RFC 8259）
  - RFC 8259では一意であることが`SHOULD`にとどまり、重複したときの挙動は実装次第です。多くの実装は黙って最後の値を採用します。

YAMLは...
- パーサーのバージョンによって、値の解釈が異なる
  - v1.1とv1.2の差など
- 暗黙の型変換がある
  - 下記サンプルを見てください。`country`はYAML 1.1系では`false`になります。またYAML v1.1に限らず 、`version`は`1.1`で浮動小数点として扱われます。
  - 例えばv1.1系では8進数の`0755`が`493`になる
- インデントによって意味と構造が崩れる
  - Helmを使ったことがある方は経験があるのではないでしょうか。インデントと空白で意味が変わるので、Helmの公式ドキュメントにTipsが記述されています。 `{{- include ... | nindent n }}`でのインデント処理について言及箇所は[こちら](https://helm.sh/ja/docs/howto/charts_tips_and_tricks/)です。

```yaml
country: no   # false (YAML 1.1)
version: 1.10 # 1.1
mode: 0755    # 493 (YAML 1.1)
```

## 百聞は一見にしかず

下記にGitHubにもあるREADMEを例示します。

なにがここで定義されているか
- レプリカ数（3）
- トラフィックの配分（25%）
- ラベル2つ
- コンテナapp1つ（イメージ、起動引数、メモリ、タイムアウト、HTTPポート、Secretへの参照）
- 起動スクリプト

```text:web.lkal
@lkal "0.1"

### Frontend web server
service "web" {
  replicas = 3
  traffic-share = 0.25
  labels { "app.kubernetes.io/name" = "web", tier = "frontend" }

  container "app" {
    image = "ghcr.io/acme/web:1.4.2"
    args = ["--port", "8080"]
    memory = 512Mi
    timeout = 30s
    port "http" { number = 8080, protocol = .tcp }
    secret = &secret/db-creds
  }

  startup =
    \\#!/bin/sh
    \\exec /app/web --port 8080
}
```

上から順にいくつか見ていきます。

### `@lkal "0.1"`
版の宣言で、すべての文書はこの行で始める必要があります。無ければLKAL独自定義のエラーコード`L105`、未対応の版なら`L207`になります。どの版の規則で読むかが、文書自体に必ず書かれます。

### `### Frontend web server`
コメントです。LKALのコメントは各行を###で始めます。#や##で始めるとL001です。コメントは直後の項目（ここではservice）に付き、整形や編集でも保たれます。

### `service "web" {`
キー`service`に、ラベル`"web"`を付けたブロックです。ラベルは入れ子のレコードを圧縮する糖衣構文なので、データとしては`service { web { … } }`と同じです。この中の項目は、`service/web/...`というパスで指せます。

### `replicas = 3` と `traffic-share = 0.25`
`3`は整数（Int）、`0.25`は小数（Decimal）です。Decimalは2進の浮動小数点ではなく、10進表記のまま保持されるので、`0.25`が丸められることはありません。キー名には`-`も使えるので、`traffic-share`は引用符なしで書けます。

### `labels { "app.kubernetes.io/name" = "web", tier = "frontend" }`
ここの`labels`は、LKAL自体のラベル構文ではありません。Kubernetesのラベルを表す、ただのキー名です。中身は文字列を2つ持つ普通のレコードです。
キー`"app.kubernetes.io/name"`は、`.`と`/`を含むので引用符が必要です。`tier`のような単純な名前は、引用符なしで書けます。

### `memory = 512Mi` と `timeout = 30s`
単位付きの量（Quantity）です。数と単位が分かれて保持されます。たとえば`512Mi`は`Number: "512"`, `Unit: "Mi"`です。

### `secret = &secret/db-creds`
他のリソースを指す参照です。データとしては`["secret", "db-creds"]`という区切られたパスとして持ちます。
YAMLの&（アンカー）とは別で、文書の中で展開されることはありません。参照先が実在するかどうかも、v0.1では検査しません。

### `.tcp`
列挙（Enum）です。

### `startup =`以下
```text:web.lkal
startup =
  \\#!/bin/sh
  \\exec /app/web --port 8080
```
各行を\\で始めると複数行の文字列になります。値は"#!/bin/sh\nexec /app/web --port 8080"で、末尾に改行は付きません


ざっとこんな感じで、型との対応を次の表にまとめます。

### 型の一覧

| パス（`service/web/`以下） | 書き方 | 型 |
| --- | --- | --- |
| `replicas` | `3` | Int |
| `traffic-share` | `0.25` | Decimal |
| `labels/"app.kubernetes.io/name"` | `"web"` | String |
| `container/app/image` | `"ghcr.io/acme/web:1.4.2"` | String |
| `container/app/args` | `["--port", "8080"]` | 文字列のList |
| `container/app/memory` | `512Mi` | Quantity |
| `container/app/timeout` | `30s` | Quantity |
| `container/app/port/http/number` | `8080` | Int |
| `container/app/port/http/protocol` | `.tcp` | Enum |
| `container/app/secret` | `&secret/db-creds` | Ref |
| `startup` | `\\`の行 | String |

## LKALが目指したところ

シンプルだが、人間にもLLMにも、アプリケーションにも優しいフォーマットを目指しました。
LLMにとってはまだ馴染みのない形式ですが、構造が{}だけで決まりインデントのずれで壊れないこと、JSONと往復できること、エラーが機械可読な形で返ることから、生成と修正のループには載せやすいと考えています。

以下がLKALフォーマットの利点です。

1. 型は値の書き方でのみ決まる
2. 曖昧な記述はエラーで落とす
3. 構造を意味づけるのは、`{}`だけ
4. 各行が単独で意味を持つ
5. 状態宣言に必要な型が基本型にある
6. 全項目を名前付きのパスで一意に指せる

例示したように、`"80"`は常に文字列になり、`80`は常に数値です。バージョンの異なるパーサーや、文脈、読み込み先の型によって解釈が変わることはありません。
また、`no`（引用符のない単語）、`0755`（0始まりの数）、`22:22`（数として解釈不能なもの）、`null`や重複キーなどは許可せず、エラーにします。
繰り返し要素はラベル付きの入れ子で表すので、どの項目もパスで一意に指せます。`service/web/port/http/number`のようにです。


ツールにも工夫をしました。

- Goの標準ライブラリでのみ実装しました
- LKAL→JSON→LKALで、9種の型を含むデータを損失なく往復できる（コメントや書き方は保たれない）
  - LKAL-JSONという形式で全9種の型情報を保ったまま変換できます
  - くわえて、型タグを文字列に展開したplain JSONへの出力も可能です
- エラーを機械で扱いやすくしました
  - エラーは行・列、固定のエラーコード、修正ヒント付きで報告され、--jsonを付けると機械可読なJSONでも出力できます

※ LKALの9種の型は、`Int`, `Decimal`, `String`, `Bool`, `List`, `Quantity`, `Enum`, `Ref`, `Record`です。

## LKALが目指さなかったところと短所

- 変数やテンプレートといった計算の仕組みも、YAMLのアンカーのような再利用の仕組みもないため、記述が冗長になり得る
- オブジェクトのリストがない
- nullがない
- 任意のJSONは取り込めず、完全なJSON互換性はない
- 整数はint64、小数は100桁まで

いずれも、曖昧さをなくし、すべての項目をパスで一意に指せることを優先した結果のトレードオフです。


## 実際に試す

```sh
go install github.com/Kaikei-e/LKAL/cmd/lkal@latest   # Go 1.27.3以上が必要
lkal check web.lkal
lkal get web.lkal service/web/container/app/port/http/number   # 8080
lkal get -r web.lkal service/web/container/app/image           # ghcr.io/acme/web:1.4.2
lkal set web.lkal service/web/replicas 5
lkal set web.lkal service/web/container/app/env/LOG_LEVEL '"info"'
```

`set`の後のファイルの差分は、`replicas`の値と、`container`ブロックの末尾に追加された`env "LOG_LEVEL" = "info"`の2箇所だけです。コメントや空行、他の項目のレイアウトはそのまま残ります。

書き間違えると、位置・エラーコード・修正ヒントが出ます。

```text
web.lkal:14:45: L102 bare word in value position
  hint: write "tcp" for a string or .tcp for an enum
```
